# دوام الميسر — أساس الإصدار 0.2.0 (تطوير مستقل)

## تحديث فرع التجربة 0.2.22 — عرض البصمات الشخصية وتنبيهات العامل
- يعرض «دوامي وتنبيهاتي» كل حركات العامل المسجلة من MB10 حتى لو كان نوعها غير محدد، مع وقتها وعددها وأول حركة وآخر حركة، دون اعتماد حضور أو انصراف غير مؤكد.
- يوضح سبب عدم تفعيل إشعارات Chrome، ويتيح إعادة ربط اشتراك الجوال بحساب العامل الحالي.
- تمنع رسالة غياب البصمة الخاطئة عندما توجد حركة حقيقية برمز غير محدد.
- لا حذف للحركات الأصلية ولا خصم مالي تلقائي.

## تحديث فرع التجربة 0.2.21 — الجلب التلقائي لبصمات MB10
- تشغيل جلب البصمات كل عشر دقائق دون فتح PowerShell يوميًا، باستخدام مهمة Windows تُثبت مرة واحدة على كمبيوتر المكتب.
- شاشة الجلب تعرض تاريخ آخر مزامنة ناجحة؛ وتسمح بالجلب الفوري عند الحاجة دون حذف بصمات الجهاز.
- دليل مفصل: [تفعيل الجلب التلقائي](docs/MB10_AUTOSYNC_SETUP.md).
- تشغيل المهمة مشروط بتسجيل الدخول إلى Windows واتصال كمبيوتر المكتب بالجهاز والإنترنت. الاستغناء عن الكمبيوتر نفسه عبر ADMS/PUSH مرحلة منفصلة تتطلب فحص الجهاز.

## تحديث فرع التجربة 0.2.20 — وصف واضح بدل «بحاجة إلى مراجعة»
- يعرض سجل الحضور والبصمة نوع الحالة (دخول مكرر، حركة غير محددة، انصراف دون حضور... إلخ) وسببها التفصيلي.
- تسري التسميات على العرض والمعاينة والطباعة وملف CSV. يمكن مراجعة الحركة الخام وتصحيحها مع تدقيق إداري دون حذف أو خصم آلي.
- لم تتغير سجلات MB10 أو بيانات الرواتب.

## تحديث فرع التجربة 0.2.19 — دقة تنبيهات العامل
- يُفرّق النظام الآن بين غياب حركة البصمة كليًا وبين وجود حركة غير محددة (مثل رمز 255)؛ في الثانية يرسل تنبيه مراجعة بدل اتهام العامل بعدم التبصيم.
- لا خصم آلي، ولا حذف أو تعديل في سجلات الجهاز.
- يجب اختبار التنبيه الفعلي على هاتف عامل مشترك قبل الاعتماد.

## تحديث فرع التجربة 0.2.18 — أسباب مراجعة البصمة وتنظيم الروابط
- `/device-attendance.html`: عرض سبب مراجعة الحركة مع الرقم الخام ورابط التصحيح الإداري إذا لزم.
- اختصار صلاحيات المستخدمين تحت «الإعدادات واللوائح»، وجلب MB10 تحت «الحضور والبصمة»، بلا أزرار عائمة جديدة.
- إصلاح إعادة التحديث غير الضرورية لرقم الإصدار في الواجهة.
- لا تتغير سجلات جهاز MB10 أو قواعد الخصومات نتيجة هذه التعديلات.

## تحديث فرع التجربة 0.2.17 — معالجة رفض Cloudflare لجلب MB10
- إضافة User-Agent مخصص ومعلن لبرنامج Python المزامنة لتجاوز الرفض المحتمل للعميل الافتراضي على نطاق Pages.
- عدم تكرار HTTP 401/403 كل خمس ثوان، مع المحافظة على مفاتيح الدخول ومنع طباعة الأسرار.
- يلزم تنزيل `tools/mb10_sync.py` الجديد على كمبيوتر المكتب وإعادة تجربة المزامنة.

## تحديث فرع التجربة 0.2.16 — حماية صفحة العامل وإشعاراته
- تتطلب صفحة العامل جلسة دخول مربوطة بعامل؛ يظهر زر تسجيل الخروج/تغيير المستخدم ورسالة واضحة قبل عرض البيانات الشخصية.
- زر تنبيه الاختبار ظاهر ويوضح سبب تعطيله حتى تفعيل اشتراك الجهاز؛ اختصار جلب MB10 للمدير والموارد البشرية.
- التنبيهات الآلية تتطلب مزامنة ناجحة من جهاز المكتب؛ لا تتغير حركات البصمة أو الرواتب.

## تحديث فرع التجربة 0.2.15 — توحيد رقم الإصدار وإعداد مفاتيح Web Push

- توثيق: [CHANGELOG_DAWAM](CHANGELOG_DAWAM.md).

## تحديث فرع التجربة 0.2.14 — تنبيهات العامل بالخلفية
- فرع العمل: `feature/dawam-0.2.0-foundation`؛ المشروع التجريبي Cloudflare Pages: `dawam-muyassar-stage` (لا يمس `main`).

## تحديث تجريبي 0.2.8 — تمييز حركات البصمة (31 أكتوبر 2026)
- **أخضر:** حضور أولي. **أحمر:** انصراف نهائي. **برتقالي:** خروج مؤقت وعودة مرتبطة به (استعذار أثناء الدوام). الحركة غير المؤكدة تظهر بلون محايد للمراجعة.
- تعرض صفحات الحضور والبصمة، وسجل MB10، وتصحيح بصمات الجهاز الألوان والأنواع؛ كما يدعم كشف الحضور ترشيح الاستعذار، ومعاينة وطباعة ومشاركة التصنيفات.
- الاستعذار يُستنتج فقط من سلسلة `حضور → خروج → عودة` للعامل نفسه في اليوم ذاته، مع احتساب مدة الانقطاع الواقعة داخل ساعات الدوام المعتمدة (الخميس إلى 13:15؛ السبت–الأربعاء إلى 13:45؛ الجمعة مستثناة).
- الإدخالات المتكررة أو غير المصنفة أو غير المطابقة لا تُعامل تلقائيًا كاستعذار مؤكد. التصحيح الإداري لا يغيّر سجلات MB10 الخام.
- **المستحقات:** تحسب المعاينة الحالية فترات الاستعذار بعد إعادة قراءة الحركات المصححة؛ لا يوجد ترحيل تلقائي للخصم أو اعتماد مالي في هذا الإصدار. يلزم اختبار البصمات الحقيقية وسياسة الرواتب قبل تفعيل الصرف.
- هذه تعديلات على **فرع التطوير التجريبي** فقط؛ لا تؤثر على فرع `main`.


**هذا الفرع للتأسيس التجريبي فقط، ولا يغيّر النشر الحالي 0.1.3 على GitHub Pages.**

المرحلة الأولى تتضمن: هيكل D1، واجهة Cloudflare Pages Functions API، تسجيل دخول آمن، صلاحيات متعددة، شاشة مستخدمين وسجل تدقيق أولي، وإجبار كلمات المرور الأولية على التغيير. لا تتوفر قاعدة حقيقية أو خادم منشور حتى ربط Cloudflare يدويًا وإجراء الاختبارات.

**الخطوة التالية:** [دليل تأسيس وربط المرحلة الأولى](docs/PHASE1_FOUNDATION.md).
